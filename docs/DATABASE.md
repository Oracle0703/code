# 数据库与迁移

Daily Workbench 使用 Electron 自带的 `node:sqlite`。数据库只在 Main 进程中打开；Renderer 不能接触 SQL、数据库文件路径或任意备份目标。

## 目录与生命周期

Main 从 `app.getPath('userData')` 推导受控的数据目录：

```text
userData/
└─ data/
   ├─ daily-workbench.sqlite3
   ├─ database-initializing-v1                     # 首次初始化未完成的耐久意图
   ├─ database-initialized-v1                      # 成功初始化的耐久哨兵
   ├─ database-replacement-v1.json                 # 仅替换进行中
   ├─ rollback-<replacement-id>.sqlite3            # 仅替换/回滚进行中
   ├─ pre-import-recovery-<replacement-id>.sqlite3 # 成功替换后保留的旧库（兼容命名）
   ├─ imports/                                     # 隔离包与 staging，仅预检/替换期间
   └─ backups/
      └─ daily-workbench-*.sqlite3
```

在 POSIX 系统上，应用会把既有或新建的 `data/`、`imports/` 与 `backups/` 目录收紧为仅当前用户可访问的 `0700`，数据库、替换文件、导入包与已完成备份使用 `0600`。Windows 依赖用户配置目录的系统 ACL；当前阶段不自行重写 ACL。

启动和恢复会拒绝符号链接或错误文件类型，并在长读取与发布前后复核文件身份、大小、时间和摘要。这一边界面向崩溃、断电、意外同步和普通文件替换；已经能够以同一系统账户持续改写应用私有目录的进程不视为隔离对手。尤其是跨平台地阻止该进程在两个系统调用之间主动交换整个目录 inode，需要平台专用目录句柄/`openat` 方案，当前版本不作此承诺。

数据库服务是应用级单例，在第一个窗口创建前打开。macOS 上关闭并重新打开窗口不会重复创建连接；正常受控退出先等待可信 Renderer 对未保存内容给出明确许可，拒绝时浏览器、终端、专注、自动化调度器与数据库保持可用。确认传输期间 Renderer 会冻结交互且在传输失败时恢复；Main 收到确认后立即禁用并隐藏窗口，再阻止新浏览器/终端操作，停止自动化和专注调度，把运行中的专注会话原子暂停，随后排空浏览器元数据、幂等终止全部 PTY，停止数据库新操作、等待正在进行的备份、checkpoint WAL 并关闭连接，最后强制销毁已批准的隐藏窗口。数据替换也必须在关闭旧连接前停止这两个应用级 Controller，重新打开验证完成后再启动。Windows 注销、关机或进程被强制终止时不能依赖 Electron 的退出事件；此时由 SQLite 事务/WAL 保证崩溃恢复，下次启动按绝对截止时间对账，未完成的 `.partial` 备份不会进入可用备份列表。

当前 schema 为 v11。v7 提供搜索索引、备份策略和数据保护状态；v8 为每个工作区追加机器本地的固定终端 Profile、本机启动目录、WSL 发行版名称与 revision；v9 追加受控自动化定义、运行状态和不可变 occurrence 账本；v10 追加固定 25 分钟的专注会话、全局未结束唯一性和不可变历史；v11 追加归档工作区恢复 revision、CAS 保护、归档元数据不可变约束与恢复时的自动化全局上限。终端会话、输出缓冲和冻结的启动描述仍只存在于 Main 运行时，应用重启或恢复工作区都不会恢复终端。机器配置进入完整 SQLite 备份，但不进入 `.dwbx` 逻辑数据包；数据库中也没有自定义命令、参数、环境变量、cron 或外部动作字段。

所有页面只能调用以下窄接口：

- 获取数据库健康状态；
- 在应用控制的目录中创建手动备份；
- 列出由应用识别的完整备份历史；
- 以备份 ID、原因、创建时间、字节数和 schema 版本组成的严格令牌恢复其中一个时间点；
- 读取或按 revision 更新应用级自动备份策略；
- 以当前工作区或全部活动工作区为范围搜索受支持的持久数据；
- 通过 Main 控制的文件选择流程导出逻辑数据包、预检导入包，并使用 opaque 导入 ID 与预览摘要确认或取消导入。
- 获取工作区原子快照；
- 创建、重命名、切换或归档受控工作区；
- 以严格字段 patch 更新指定活动工作区的界面偏好。
- 获取指定活动工作区的收件箱快照；
- 创建、分类和软归档收件箱条目；创建响应同时返回事务后快照与 Main 实际插入的 opaque ID；
- 使用 Main 签发、由单调时钟判定有效期的一次性短期令牌撤销刚完成的归档。
- 获取指定活动工作区的完整任务快照、Main 计算的本地 `todayDate` 及固定 7 日计划映射；
- 创建或重命名任务，更新固定状态，并通过 `day-0` 至 `day-6`/`none` 意图在当前 7 日窗口内安排、移动或移出计划；
- 在单一事务中把收件箱条目转换为带唯一来源关系的任务。
- 获取指定活动工作区的 Markdown 笔记快照；
- 创建、按 revision 更新或软归档笔记，并在单一事务中把收件箱条目转换为真实笔记；
- 获取指定活动工作区由 Main 计算的当前 7 日日程；
- 在当前 7 日窗口内创建、按 revision 更新或软归档固定类型时间段。
- 获取指定活动工作区的自动化定义与运行摘要；
- 新建默认停用的每日/每周规则，并返回事务后快照与 Main 实际插入的 opaque ID；按 revision 编辑、启停或软归档；动作只允许创建今日任务或 Markdown 笔记；
- 在界面展示已保存动作并获得显式确认后，以自动化 ID 与 revision 请求立即运行一次。
- 获取指定活动工作区视角下的全局未结束专注会话与今日完成轮次；
- 开始固定 25 分钟的自由专注或关联当天未完成任务，按 session ID 与 revision 暂停、继续或取消。
- 获取指定活动工作区的浏览器标签、活动标签状态和收藏夹；
- 新建、激活或关闭标签，持久化受控 URL/标题，并切换或移除收藏夹。
- 读取指定活动工作区的终端能力与机器本地偏好；
- 按 revision 更新固定 Profile、由 Main 原生目录选择器授权或重置本机启动目录，并以 capability revision 绑定 opaque WSL 发行版选择。

自动化接口不接受 Renderer 提供的 cron、可执行文件、参数、环境变量、URL、Webhook、通知或 AI 动作；立即运行也只接受目标工作区、自动化 ID 与 expected revision，不能携带动作、运行时间或调度状态。专注接口不接受时长、截止时间、状态、完成时间或持久化日期。路径、WSL 发行版名称、SQL、迁移版本和新的备份原因也不作为通用 Renderer 输入；导出、导入和终端目录只由 Main 的受控文件选择流程决定。备份恢复只接受完整匹配现有列表项的元数据令牌，不提供文件名、任意路径、外部 SQLite 或删除能力；逻辑导入也不是把外部 SQLite 文件直接交给数据库连接。

手动备份的成功响应本身就是耐久提交事实。Renderer 会冻结返回的 ID、受控文件名、创建时间、字节数、固定 `manual` 原因与 schema 版本，并要求管理快照中恰有一个全部字段精确匹配的条目；不会按最新时间、文件名或列表位置猜测。事务后快照被更晚读取淘汰时，Controller 会从 ref-backed committed snapshot 开始，最多执行两轮带 generation 的权威读取并最终复查 ref。Main 已成功但 exact 条目仍不能提交时，只能发布跨页面的“备份已创建，请勿重复创建”恢复态，设置页和命令面板的创建入口同时失败关闭；重新读取保持 single-flight，不调用第二次创建。missing、重复 ID、任一元数据不匹配、非手动响应、读取异常或 commit 被淘汰都不能降格成可重试创建失败。后续 exact 事件或读取只解除一次警告；同 revision 的迟到快照不能隐藏已确认条目。取消/失败的数据替换和关闭审批会保留旧数据库对应身份，只有恢复实际进入重启或导入提交成功才清除。

## 连接策略

数据库适配层统一启用以下约束：

- foreign keys；
- WAL journal；
- `synchronous=NORMAL`；
- 5000ms busy timeout；
- `trusted_schema=OFF`；
- defensive mode；
- 禁止扩展加载与双引号字符串兼容行为。

Repository 负责 SQL 与严格行映射，Service 负责生命周期、串行化、事务、不变量和对外返回值。业务页面只能通过 `Renderer → Preload → 可信 IPC → Service → Repository` 接入。数据库元数据与工作区、收件箱、任务、笔记、日程、浏览器标签和收藏夹的启动校验在同一事务提交，校验失败不会留下已更新的 `last_opened_at` 半状态。

工作区、收件箱、任务、笔记、日程或浏览器事务如果无法可靠回滚，数据库服务会立即进入 fatal 状态：当前错误向上返回，已排队及后续读取、写入和备份全部拒绝，直到连接关闭并由新实例重新打开。应用不会在事务结果未知的连接上继续服务。

## 迁移规则

迁移源文件放在 `migrations/`，通过 `?raw` 在构建时嵌入 Main bundle，避免安装后依赖源码目录。

1. 版本必须从 1 开始连续递增。
2. 已合并或发布的迁移禁止修改、重排或删除，只能追加新文件。
3. 每条已应用迁移记录版本、名称、SHA-256 校验和与应用时间。
4. 启动时会比较代码中的迁移与数据库历史；缺号、未知版本、名称或校验和漂移都会阻止打开。
5. 待执行迁移在 `BEGIN IMMEDIATE` 事务内应用；任何错误都会回滚本次启动中的全部待执行迁移。
6. 迁移 SQL 禁止自行提交、开启保存点、执行 `PRAGMA` 或 `ATTACH/DETACH` 外部数据库；事务、版本、连接安全设置和数据库路径只由迁移框架控制。
7. 迁移成功后必须通过 quick check、foreign-key check，并重新核对 WAL、foreign keys、`synchronous=NORMAL`、5000ms busy timeout 与 `trusted_schema=OFF`。

已有主数据库需要升级时，应用会先生成 `pre-migration` 一致性备份；备份创建或校验失败时不会执行迁移。新建空数据库不会生成无意义的迁移前备份。唯一例外是 `imports/` 中由已识别应用备份稳定复制出的隔离副本：它的规范源已经由备份管理器保留，因此副本仍走完整迁移/初始化链，但不会在深层临时目录中再生成一份冗余迁移备份。

当前迁移版本：

- `0001_database_foundation.sql`：应用元数据与迁移底座；
- `0002_workspaces.sql`：工作区、工作区偏好、单例当前选择、活动名称约束和归档保护触发器。
- `0003_inbox.sql`：按工作区隔离的收件箱条目、固定分类、软归档索引和归档工作区写保护。
- `0004_tasks.sql`：按工作区隔离的任务、固定状态、民用日期计划、唯一收件箱来源和归档工作区写保护。
- `0005_notes_schedule.sql`：按工作区隔离的 Markdown 笔记与单日日程、revision 并发保护、收件箱唯一来源和软归档保护。
- `0006_browser_tabs_bookmarks.sql`：按工作区隔离的浏览器标签、活动标签状态与收藏夹、数量上限、revision 和归档工作区写保护。
- `0007_search_data_protection.sql`：六类业务数据的外部内容 FTS5 trigram 索引、同步触发器与回填，以及应用级备份策略和运行结果状态。
- `0008_terminal_workspace_preferences.sql`：每工作区一行的机器本地终端 Profile、本机 CWD、WSL 发行版选择、revision 与归档写保护。
- `0009_scheduled_automations.sql`：每日/每周固定动作定义、运行状态、不可变 occurrence 账本、数量上限与工作区归档停用。
- `0010_focus_sessions.sql`：固定 25 分钟专注、全局未结束唯一性、状态转换、工作区归档取消与不可删除历史。
- `0011_workspace_recovery.sql`：归档工作区恢复 revision 与 CAS、归档元数据不可变和时间顺序、自动化全局上限及归档工作区自动化运行状态/occurrence 写保护。

v11 之后只能追加 `0012_*.sql`（version 12）或更高版本；自定义测试迁移也不能复用 version 11。

工作区 v2 始终保证至少一个活动项、一个有效当前选择以及每个工作区一条偏好。归档保留工作区、偏好和全部关联业务行；Renderer 不能自定义归档时间，也没有永久删除入口。名称在 Main 中执行 Unicode NFKC 规范化并生成唯一键，颜色只接受内置调色板。

v11 为每个工作区追加不可删除的 recovery revision。归档和恢复都会由数据库触发器把它精确推进一次；恢复必须提交归档快照中的 `workspaceId`、`expectedRevision` 和显式名称，并在同一事务中以 revision CAS 清除 `archived_at`。revision 已变化或工作区已恢复时，迟到请求会失败并要求重新读取快照。归档期间可能出现同名活动工作区，因此名称冲突不会被后端静默加后缀；用户必须显式选择另一个合法名称后重试。

恢复只让持久化工作区重新进入活动集合，不写入 `workspace_app_state`，所以不会自动切换当前工作区。归档时已被停用并清空 `effective_at` 的自动化保持停用；Service 预检与数据库触发器共同保证恢复后全部活动工作区的未归档自动化定义不超过 100 条。归档事务已把该工作区未结束的 Focus 会话写为 `cancelled`，终态不会因恢复而改写；归档时被清理的浏览器页面、下载、PTY 和 AI 请求等 Main 运行时也不会重建或复活。永久删除仍不暴露，恢复前后的持久数据继续进入完整备份和受支持的逻辑数据包。

工作区界面偏好继续使用既有 `workspaceId + strict field patch` 写入，不给数据库行增加 Renderer 请求身份。Renderer 在内存中按 `workspaceId + field` 记录 epoch 与单调 sequence；只有与当前字段身份精确相同的成功才能清除 dirty，只有同一当前身份的失败才能进入可见保存错误，而 pending cleanup 只结算其原请求 epoch。这样同一字段的值从 A→B→A 时，第一笔 A 即使最后返回，也不能凭值相等误认成第三笔 A 已提交。重试只发送当前 epoch 仍未解决字段的最新值；读取重试或已确认提交的数据替换建立新 epoch，取消或失败的数据替换保持当前 epoch。旧 epoch 的成功、失败和清理结果全部隔离，不会清除当前失败或阻止当前重试。

这项约束只修正 Renderer 对偏好保存回执的归属，不改变工作区 CRUD 的事务或快照语义，也不新增提交后 CRUD 对账。Main 的偏好 Repository/Service、preload/IPC 合约、`workspace_preferences` 表、schema v11 和 `.dwbx` v3 均保持不变。

从原型版本首次进入 v2 时，Renderer 会严格读取旧 `localStorage` 中合法的页面、主题和布局值，并只在数据库仍为单一默认工作区时导入；只有 SQLite 写入成功后才清理旧键。旧版硬编码工作区选择不会被当作真实身份导入，写入失败时会保留可重试的 dirty patch 和旧键。

收件箱 v3 不导入界面中的演示条目，也不会把原型 `localStorage` 任务当作真实收件箱数据。条目允许重复正文，分类只接受 `uncategorized`、`task`、`note`、`link`；其中 `task` 只是处理意图。归档工作区中的条目原样保留，但触发器和 Service 都拒绝继续修改。

`inbox:create` 沿用既有输入与通道，成功响应新增同一事务后的 `inboxSnapshot` 和 Main 实际插入的 `createdEntryId`；这不新增 schema、migration 或 IPC 通道。Renderer 先提交事务快照；若它被较新序号抢先，最多再做两次权威读取，并只接受当前工作区内唯一匹配该 opaque ID 的条目。Today 与全局快速记录同步成功后仍留在原页，并共用统一回执；只有用户显式打开时，Renderer 才再次 fresh-read 并精确复核。若 Main 已落库但两次读取后仍无法提交快照，输入面会关闭或清空并显示独立警告，要求重新读取且不要重复添加；重新读取只有在 exact ID 存在且快照提交成功后才发布回执。真正的创建请求失败仍保留原输入供重试。目标缺失、已归档、工作区 activation 或较新请求变化时不会按正文、时间或列表位置模糊回退。

任务 v4 也不会导入 `daily.today.tasks` 中的演示任务，或自动转换既有 `task` 分类收件箱条目。任务状态固定为 `todo`、`in_progress`、`completed`；`planned_for` 只保存 Main 计算的本地民用 `YYYY-MM-DD` 或 `NULL`，完成状态与 `completed_at` 必须一致。Renderer 只能提交 Main 快照签发语义下的 `day-0` 至 `day-6` 或 `none` 固定计划意图；Service 在数据库 FIFO 操作真正执行时把 token 映射到民用日期，不能由页面伪造日期、ID、时间戳或来源关系。这个扩展不改变 v4 表结构或当前 schema 版本。

`task:create` 沿用既有输入与通道，在同一个 Main 事务中创建任务，并返回事务后的 `taskSnapshot` 与实际插入的 opaque `createdTaskId`。Today、Tasks 与命令面板中的手动创建成功后仍留在发起页面并显示回执；只有用户显式打开时，Renderer 才 fresh-read 当前工作区任务、只按该 ID 精确复核，并在权威快照提交后进入 Tasks 的编辑界面。目标缺失时会留在原页报错，工作区、页面、反馈或较新请求变化时失败关闭，不会按标题、计划日期或列表位置回退。若 Main 已提交创建但 Renderer 仍无法提交权威快照，创建框会关闭并明确提示刷新且不要重复创建，同时不发布未经确认的成功回执。这个返回契约不新增 schema 或 migration；当前 schema 仍为 v11，`.dwbx` 仍为 v3。

显式收件箱转换在一个事务内创建任务、写入唯一 `source_inbox_entry_id` 并软归档来源条目。任一步失败都会整体回滚；同一来源不能转换两次。成功响应中的 `createdTaskId` 是 Main 在该事务中实际插入的任务 ID。归档工作区中的任务和来源关系继续进入备份，但不能再修改。

笔记 v5 不导入 Renderer 中的演示卡片，也不会因为收件箱分类为 `note` 就自动创建笔记。标题最多 200 个 Unicode code point；正文最多 100,000 个 code point，并把 CRLF/CR 统一为 LF。正文允许 Markdown、普通换行和 Tab，但拒绝 NUL、畸形 Unicode 与不支持的控制字符。创建时 revision 为 1；更新和软归档必须携带当前 `expectedRevision`，并在数据库内只递增一次。已归档笔记和归档工作区笔记不可修改，笔记不提供永久删除。

`note:create` 沿用既有输入与通道，在同一个 Main 事务中返回事务后的 `noteSnapshot` 与实际插入的 opaque `createdNoteId`。Notes 页面只在该 ID 唯一存在且快照真正提交后清除草稿并进入新笔记；若事务快照被较新读取淘汰，Renderer 最多再做两次权威读取，并在每个异步边界后复核当前 workspace activation。Main 已落库但仍无法同步时，App 按 workspace/page generation activation 保留 exact ID 和原内容；即使 Notes 组件因同工作区切页而卸载，返回后仍会重建不可再次提交的已落库内容，并显示“重新读取且不要重复保存”的独立警告。确认进行中或警告未恢复时会阻止工作区切换、新建或归档当前工作区以及跨工作区搜索；只有精确恢复或真正获批并提交的数据替换才使旧状态失效。真正的 IPC 创建失败才保留可编辑草稿供重试。这个协调不新增 schema、migration 或 IPC 通道；当前 schema 仍为 v11，`.dwbx` 仍为 v3。

`note:update` 和 `note:archive` 继续返回事务后的完整 `noteSnapshot`，但 Renderer 不把 Main 已成功的响应降格为“可以再次提交”的错误。更新只接受同一工作区内唯一匹配原 ID、规范化标题/正文、预期 revision、来源 ID 与创建时间的行；实质更新要求时间不回拨，无内容变化则 revision 与更新时间都必须保持原值。归档只在同一工作区已提交活动快照中确认该 ID 已消失。事务响应无法提交时，Renderer 会检查最新 committed ref、最多执行两次权威读取并做最终 ref 复查；任一 `commit=false`、身份漂移、工作区/activation 变化或迟到结果都失败关闭。

Main 已提交而 Renderer 仍无法确认时，App 保存精确 mutation intent 与事务快照，跨同工作区切页重建只读的已保存或已归档内容，并要求重新读取、禁止重复保存或归档；更新只有在精确行提交后才清草稿，归档只有在缺失事实提交后才清 selection。同一工作区的手动笔记创建、更新、归档、收件箱转笔记、AI 保存和立即运行笔记输出覆盖完整写入与对账周期的单飞边界；任何精确笔记警告未恢复时继续阻断竞争写入、工作区变更和跨工作区搜索，恢复读取重新持有同一协调器。取消备份恢复、取消原生替换确认或导入失败都不清除该恢复态，只有已批准并提交的数据替换才使其失效。这个变化只收紧 Renderer 发布契约，不改变 Main 事务、IPC、schema v11 或 `.dwbx` v3。

显式“收件箱转笔记”在一个事务内归档来源、创建笔记并建立唯一来源关系。任务与笔记共享同一个来源排他边界：同一收件箱条目不能同时转换为任务和笔记，已关联来源不能恢复。转换任一步失败都会整体回滚；成功响应中的 `createdNoteId` 是 Main 在该事务中实际插入的笔记 ID。

两个 created ID 只扩展既有转换响应，不新增 IPC 通道、schema 或 migration。Main 的事务提交成功后，Renderer 必须同时提交目标快照与已归档来源的收件箱快照；若响应只同步一侧，会最多再做两轮权威读取，只接受当前工作区内唯一匹配 created ID 与原始 `sourceInboxEntryId` 的目标，并确认来源不再出现在活动收件箱中。任一侧仍无法确认时，界面会保留 exact ID 与来源 ID 的独立警告，要求重新读取且不要重复转换；同一工作区的所有转任务与转笔记 mutation 也共享单飞锁，第二个来源不能静默淘汰仍在对账的第一笔转换。转笔记警告还会阻断竞争笔记写入、工作区变更与跨工作区搜索，且恢复读取重新持有笔记协调器；转任务警告仍按既有 activation 语义被工作区切换淘汰。转换成功后界面仍停留在 Inbox；用户显式选择打开时，Renderer 会 fresh-read 对应快照，同时复核精确 created ID 与原始来源，并只在快照提交到当前工作区 activation 后导航。目标缺失、来源变化、切页、较新反馈、工作区 A→B→A、已获批的数据替换或迟到响应都不会按标题、时间或列表位置回退到其他记录；取消恢复或导入失败不会提前清除原数据库对应的警告。

日程 v5 保存真实的单日时间段，不包含重复、提醒、通知或外部日历同步。类型固定为 `focus`、`meeting`、`review`、`personal`；`scheduled_for` 是本地民用 `YYYY-MM-DD`，时间范围使用 `start_minute`/`end_minute`，满足 `0 <= start < end <= 1440`。Renderer 提交的 `expectedDate` 必须位于 Main 在数据库 FIFO 操作执行时计算的 `[todayDate, todayDate + 6]` 窗口，不能越过过去或第 8 天；更新和软归档也必须携带当前 revision。日程日期不可原地修改，归档项和归档工作区日程不可再修改，日程不提供永久删除。这个扩展不改变 v5 表结构、当前 schema v11 或 `.dwbx` v3。

`schedule:create` 沿用既有输入与通道，在同一个 Main 事务中生成 ID、插入日程，并返回事务后的 `scheduleSnapshot` 与实际插入的 opaque `createdScheduleId`。Today 与 7 日计划创建成功后仍留在原位置；用户显式编辑时，Renderer 会 fresh-read 当前工作区日程，只接受该 ID 与原持久化日期的唯一匹配，并在权威快照提交后打开编辑窗口。目标缺失、跨午夜、切页、较新创建、工作区 A→B→A 或迟到响应都不会按标题、类型、时段或列表位置回退。若日程已经提交但 Renderer 在有界重读后仍无法同步，创建窗口会关闭并显示独立的“刷新且不要重复创建”警告，不发布未经确认的成功回执；当前 schema 仍为 v11，`.dwbx` 仍为 v3。

既有 `schedule:update` 与 `schedule:archive` 仍在单个 Main 事务中返回事务后的完整快照；Renderer 不把 IPC 成功直接等同于列表已提交。更新按同工作区、目标日期、精确 ID、创建时间、规范化标题/类型/时段及预期 revision 验证唯一行，无变化更新保持 revision 与 `updatedAt`；归档只在覆盖目标日期的快照中按精确 ID 缺失确认。响应快照若被更晚读取淘汰，会先复查 Renderer 最新已提交快照，再最多权威重读两次；跨午夜只能用已经由可信 Main 响应精确确认的结果配合新日快照收口，不能把普通“目标不在新窗口”当作归档或更新成功。仍无法确认时，App 保留精确写入身份和“已提交、勿重复”警告，重新读取不重放事务，并在恢复前阻止同工作区其他日程写入、工作区切换和日程搜索跳转。成功的数据替换使该 Renderer 恢复状态失效，取消或失败保持原状态；数据库 schema、migration、IPC 和 `.dwbx` 格式均未改变。

Today 的今日任务、进度、今日日程和滚动 7 日计划都使用这些真实行。任务、日程与搜索共用纯民用日期加法；Renderer 会在本地跨午夜、窗口重新聚焦或页面重新可见时丢弃旧日快照并重新读取，并同步遮蔽仍属于旧日期的任务、日程或专注快照，避免系统睡眠或时区变化后混合显示或写入过期数据。

浏览器 v6 不导入旧版仅运行时的 URL、历史或页面会话。首次访问活动工作区时，Service 会在单一事务中创建一个默认标签和对应的 `browser_workspace_state`；活动工作区始终至少保留一个标签，关闭最后一个标签会原子重置该行。每个工作区最多 12 个标签和 500 个收藏夹，收藏 URL 在工作区内唯一，只允许受控 HTTP(S) 地址。

浏览器标签、状态和收藏夹的 ID、时间戳与 revision 都由 Main 生成或推进。状态更新必须严格执行 `revision + 1`，标签与状态时间不能回拨，启动和备份还会验证状态时间不早于同工作区的标签或收藏夹；标签工作区不可改写，活动标签必须引用同工作区现存标签。远程页面标题会移除控制字符和双向文字覆盖/隔离符后再持久化，防止标签视觉欺骗。高频 URL/标题事件在 Main 中按标签合并为有界写入，状态切换与受控退出会排空最终期望值。归档工作区的全部浏览器持久数据继续进入备份，但 Trigger 与 Service 都拒绝继续写入或删除。Cookie、登录态、网页前进/后退历史和下载记录不进入 SQLite。

## 终端机器偏好

v8 的 `workspace_terminal_preferences` 与 `workspaces` 一一对应。迁移会为所有既有工作区写入 `system-default`、用户 home、系统默认 WSL 发行版和 revision 1；后续创建工作区由触发器在同一事务中生成同样的安全默认行。偏好行不能删除或改写所属工作区，归档工作区不能再更新；每次修改必须精确推进一个 revision，旧请求会被拒绝。

Profile 只接受共享协议中的固定 ID。本机启动目录以平台和绝对路径成对保存，但只能由 Main 的原生目录选择器产生；读取与备份校验会重新验证良构 Unicode、长度和绝对路径，能力快照、创建及重启还会重新验证当前平台与目录可用性，不可用时不会回退。WSL 只保存 Main 已发现的发行版名称；Renderer 看到并提交的是绑定当次 capability revision 的 opaque ID，因此刷新能力或发行版列表变化后，旧选择请求不能落库。WSL CWD 不进入 schema，本阶段一律从发行版 Linux home 启动。

这些字段是机器授权状态，不是可移植业务数据。完整 SQLite 备份会保留它们，便于同机灾难恢复；`.dwbx` 导出不序列化该表。导入 v7/v8 legacy v1、v9 v2 或 source schema v10/v11 的 v3 数据包时，一律构建当前 v11 staging 数据库；工作区插入触发器只创建安全默认终端偏好，不把来源机器的 Profile、路径或发行版带到目标机器。

## 定时与手动自动化

v9 的 `automations` 按工作区保存定义，`automation_run_state` 一对一保存最后尝试、最后成功、失败退避与下一次重试，`automation_occurrences` 以 `(automation_id, occurrence_date)` 保存不可变成功账本。每个计划 occurrence 成功执行时，会在同一 `BEGIN IMMEDIATE` 事务中创建任务或笔记、写 occurrence 并推进成功状态；任一步失败都会整体回滚，不能出现有输出无账本或有账本无输出。

新建定义固定为停用且没有 `effective_at`，显式启用后才从该时刻开始计算计划。计划只接受每日/每周、本地分钟和每周星期；动作固定为 `create-today-task` 或 `create-note`，动作类型创建后不可修改。每工作区最多启用 25 条，全部活动工作区最多保留 100 条活动定义。工作区归档会在同一事务中停用其规则；已归档定义、occurrence 与运行状态不能由普通业务流程删除或改写。

`automation:create` 沿用既有输入与通道，在同一个 `BEGIN IMMEDIATE` 事务中生成 ID、插入默认停用的规则，并返回事务后的 `automationSnapshot` 与实际插入的 opaque `createdAutomationId`。创建成功仍留在发起页面；用户显式打开时，Renderer 会 fresh-read 当前工作区规则，只接受该 ID 的唯一匹配，并以权威快照中的当前 revision 打开编辑窗口。目标缺失、重复 ID、工作区 A→B→A、切页、较新创建或迟到结果都不会按名称、计划或列表位置回退。若规则已经提交但 Renderer 在有界重读后仍无法提交权威快照，创建窗口会关闭并显示独立的“刷新且不要重复创建”警告，不发布未经确认的成功回执。这个返回契约不新增 schema 或 migration；当前 schema 仍为 v11，`.dwbx` 仍为 v3。

调度器是应用级单例，最长每 60 秒唤醒一次并保持 single-flight。应用关闭期间不运行，也不回放全部历史；启动、系统恢复或定义变化后的评估只选择每条规则最近一次已经到期且晚于 `effective_at` 的 occurrence。成功水位和唯一主键共同防止重复；失败按有界错误码从 5 分钟开始、最长 6 小时退避。

立即运行是与调度账本分离的窄写入。可信 Renderer 必须先展示已保存动作并取得用户确认，随后只提交 `{workspaceId, automationId, expectedRevision}`。Main 在 `BEGIN IMMEDIATE` 事务中重新读取活动工作区与未归档定义、核对 revision，并按数据库中持久化的任务或笔记动作创建输出；启用和停用的活动定义都可以手动运行，Renderer 不能替换标题、正文、动作类型或时间。成功只返回工作区、自动化、输出类型与 opaque 输出 ID；失败会回滚，不留下半个输出。

Main 返回成功表示输出事务已经提交，但 Renderer 只有在对应任务或笔记快照中唯一确认该 opaque ID、并把权威快照提交到当前工作区后，才发布普通成功反馈。同一工作区的手动运行在这个对账完成前保持 single-flight；响应对应的输出尚未进入 Renderer 已提交快照时最多权威重读两次，仍无法提交则保留精确输出身份并提示重新读取、不要重复运行。恢复和后续显式打开都不得按标题、动作类型、时间或列表顺序回退。计划运行的 changed 事件不携带输出 ID，不能替代手动运行响应中的精确身份。

手动运行不会更新 `automations.enabled`、`effective_at` 或定义 revision，也不会写入 `automation_run_state`、`automation_occurrences`，不会推进成功水位、失败退避或下一次计划时间。它不消费相邻的计划 occurrence；调度器仍按原定义和账本独立执行。

完整 SQLite 备份保留定义的启停状态、运行状态和 occurrence 账本，保证同机恢复后不会重做已成功计划。`.dwbx` v2/v3 只序列化定义，不序列化 `effective_at`、运行状态或账本；导入 staging 无条件把定义置为暂停并生成空运行状态，必须由用户在目标数据库中重新启用。当前不提供 cron、条件触发、多步骤流程、Shell/终端/WSL 命令、外部网络、系统通知或 AI 动作。

## 专注会话

v10 的 `focus_sessions` 保存工作区、可选任务、创建时的 Main 本地日期、固定状态、剩余秒数、绝对截止时间、revision 与终态时间。固定一轮为 1500 秒；数据库用 partial unique index 保证全局最多一条 `running`/`paused` 会话，工作区切换不会转移或取消它。

开始会话时，可选任务必须属于同一活动工作区、计划到 Main 当前本地日期且未完成。Renderer 不能提交时长、状态、剩余时间、截止时间、日期、ID 或时间戳；暂停、继续和取消必须同时绑定原工作区、session ID 与当前 revision。状态转换只允许 `running ↔ paused`、`running → completed/cancelled` 与 `paused → cancelled`；Main 的内部 checkpoint 只能在 deadline 逐字不变时严格减少 running 的剩余值。每次 mutation 精确递增一次 revision；终态、工作区、任务、创建日期和创建时间不可改写，记录不提供永久删除。

Main 的应用级 Controller 以持久化 `deadline_at` 为权威，并用单调时钟维护不会回增的剩余上限，最长每 60 秒将更小的上限 checkpoint 到 SQLite；系统时间回拨不会延长原 deadline，系统恢复和启动时立即对账。审计时间戳继续保持逻辑单调，回拨后可以晚于独立的倒计时 deadline。到期会在单一数据库事务中写为 completed 和剩余 0。正常退出或数据替换先把 running 原子暂停再关闭数据库；异常退出无法依赖回调，下次启动会按原绝对截止时间决定完成或保留剩余时间。归档所属工作区会在同一归档事务中取消未结束会话。

每个 Focus 快照除全局未结束会话和当天完成轮次外，还在同一读事务中返回请求工作区、`todayDate` 内最近一条终态的最小摘要。Repository 同时查询 `completed`/`cancelled`，并按 SQLite `rowid` 的持久插入顺序取最后一条；会话只追加、终态不可改且全局最多一个未结束会话，因此新会话的顺序不依赖可能回拨的墙上时间。摘要只包含 session/workspace/task 身份、终态和对应的 `completed_at` 或 `cancelled_at`。因此较新的取消会话不会让较早的完成会话重新触发任务收尾，Renderer 也无需提交历史查询参数或猜测完成身份。

该摘要只为显式 UI 收尾提供只读事实，不把 Focus 与任务状态绑成一个自动事务。用户点击后仍通过既有任务快照与 task ID 精确复核，再显式把该任务设为 completed；不点击时任务行、`updated_at` 与 `completed_at` 完全不变。schema v11、`.dwbx` v3 和 Focus 状态机均未因此扩展。

完整 SQLite 备份保留全部专注历史及原表插入顺序。`.dwbx` v3 省略 cancelled 记录，并在导入时按可移植记录的规范顺序重建表，因此不承诺保留源库“最近终态”的因果身份；尚未到期的 running 在导出时按绝对截止时间计算剩余值并序列化为 paused，已经到期但尚未持久对账的 running 只在包中投影为 completed，不改写源库。导入只接受 paused/completed，且最多一条 paused。完成记录保留创建时的 `local_date`，Today 的完成轮次不会因之后切换时区而改写历史。

## 全局搜索

v7 为收件箱、任务、笔记、日程、浏览器标签和收藏夹建立外部内容 FTS5 trigram 索引；迁移会回填既有 v1–v6 数据，后续正文、标题或 URL 变化由数据库触发器同步。索引不复制工作区身份或归档状态，查询仍回连原始业务表，只返回活动工作区中的未归档业务数据。

查询先执行 Unicode NFKC 规范化，长度限制为 2–120 个可见 code point。两个字符的查询使用转义后的 `LIKE`，三个字符以上使用转义后的 FTS phrase；调用者只能选择当前工作区或全部活动工作区，不能提交 SQL、FTS 运算符或任意排序。任务等结果沿用既有活动数据范围，日程结果只覆盖 Main 在数据库队列操作执行时计算的当前 7 日窗口。每种结果最多 8 条，总计最多 40 条，并显式报告被截断的类别。

## 备份、导出与导入

备份使用 SQLite online backup API 写入同目录的唯一临时文件，验证快照可只读打开且通过迁移、工作区以及对应 schema 版本的全部收件箱、任务、笔记、日程、专注、浏览器标签、收藏夹和自动化定义/运行账本行映射后，再原子重命名为最终文件。完整历史列表会忽略临时文件、旁路文件和符号链接；Renderer 得到的是序列化元数据，不是绝对路径。

v7 的自动备份策略是应用级单例，默认关闭；启用后只能选择每日或每周、本地分钟与 1–90 个保留数量，并通过 revision 防止旧设置覆盖新设置。调度状态记录最近尝试、成功 bucket 和有界失败码；同一轮评估保持 single-flight。只有快照创建和保留清理都成功后才推进 bucket；任一步失败都不会伪装成成功，而会从 5 分钟开始、最长 6 小时指数退避并重跑完整备份轮次。执行删除时会在同一个数据库队列操作中重新读取最新保留数量，避免已提交的新设置被旧值覆盖。

保留策略只清理超额的 `scheduled` 备份；每次删除前会重新验证本轮新快照仍是可用的 `scheduled` 备份。手动、迁移前、导入前备份和 `pre-import-recovery-*.sqlite3` 都不会被自动删除。

时间点恢复只面向这份受控历史，不提供系统文件选择器。Renderer 必须原样回传所选项的备份 ID、原因、创建时间、字节数和 schema 版本；Main 会把五个字段作为同一个乐观并发令牌，重新定位唯一文件并在复制前后验证文件类型、元数据、SQLite 内容和身份稳定性。初次稳定复制的 SHA-256 还会进入 Main 内部恢复凭证；全运行时冻结后的第二次复制必须与其逐字相同，不能用相同元数据和大小的另一份有效 SQLite 替换用户已经确认的目标。任何字段或内容漂移、缺失、歧义、旁路文件或符号链接都会拒绝恢复。源备份始终以只读验证和稳定复制方式使用，迁移与归一化只发生在 `imports/` 下的唯一副本中，因此 v0–v10 旧备份可以沿正常迁移链升级到 v11，而历史源文件保持逐字不变；隔离初始化显式标记“源已保留”，禁止在 `imports/.../backups` 中生成嵌套迁移快照，从而保持单一恢复来源并避免 Windows 深路径放大。完成的 staging 仍是 schema v11；这一流程不改变当前 schema 版本或 `.dwbx` v3 格式。

恢复 staging 会从当前数据库覆盖保留 `backup_policy` 和 `backup_run_state`，避免回到旧时间点后意外改变现行备份计划或重复旧调度 bucket。备份中的自动化定义、运行状态与 occurrence 历史仍保留，但所有定义都会停用并清空生效时间；恢复后必须由用户重新启用。备份中唯一 `running` Focus 若在准备时已经到期就结算为 `completed`，否则降为 `paused`；既有 paused/completed/cancelled 历史保持不变。所有工作区的浏览器与终端面板偏好都会置为关闭，进程重启则释放原运行时浏览器视图、下载、PTY 和 AI 请求，不能从 SQLite 快照复活它们。

用户在 Renderer 中确认严格目标后，Main 仍会显示原生破坏性确认，并在允许关闭前阻止并发备份、导出、导入或另一恢复。全运行时冻结后会再次验证 staging，为当前数据库创建并重新验证一份 `pre-import` 安全备份，再复用既有 v1 replacement marker、rollback、重启提交与失败回滚协议；恢复安装不引入另一套热交换路径。当前数据库外的 API key、浏览器 Cookie/登录态、下载记录与磁盘文件不会随 SQLite 时间点回滚，既有备份目录也不会被旧库覆盖。

逻辑导出包使用版本化、规范化 JSON 行格式。source schema v10 和 v11 都使用 `.dwbx` v3，记录工作区、界面偏好、收件箱、任务、笔记、日程、浏览器标签、状态、收藏夹、自动化定义和未取消专注记录；v11 没有提升包版本，也不把内部 recovery revision 序列化为 Renderer 可伪造的恢复状态。数据包不包含自动化运行状态/occurrence、Cookie、登录态、下载、终端进程、机器终端偏好或数据库内部索引。Manifest 固定记录源应用/schema 版本、分类型计数和正文 SHA-256；解析同时限制包大小、单条大小、记录数、UTF-8、字段集合和对象深度。保存对话框返回后，Main 会在读取数据库前冻结目标的“缺失或既有文件身份”；同目录临时文件完成写入与 `fsync` 后，只有目标仍保持该状态才会原子发布。目标被创建、替换或修改时导出拒绝覆盖；发布后还会逐字回读并同步父目录。

导入不是合并外部表，也不接受任意 SQLite 文件。包会先进入受控隔离目录，校验摘要与记录关系，再从空库应用完整 v1–v11 迁移并构建、验证一个 schema v11 的全新 staging 数据库；无论来源是 `.dwbx` v1、v2 还是 v3，都不会生成旧 schema staging。预览使用有时限的 opaque ID 和摘要，确认时再次核对 staging/package 文件未变化。数据库替换协议要求先创建并重新验证 `pre-import` 一致性备份、冻结写入并关闭连接，再在重启阶段以 crash marker 驱动原子替换；任一安装或重新打开校验失败都回滚到原数据库。

成功提交不会直接删除唯一 rollback，而会先将其验证并原子发布为 `pre-import-recovery-<replacement-id>.sqlite3`，再验证新库和该恢复副本；文件名为兼容既有替换协议而保留，语义同时覆盖导入与备份恢复。它不进入普通备份列表，也不受 scheduled retention 管理。当前 UI 不提供自动清理或直接恢复这些 retained recovery 文件，因此每次成功替换都会保留一份旧库，同时普通备份列表中也保留对应的 `pre-import` 安全快照。启动时若 marker 存在，会按阶段继续提交或回滚；marker 缺失时仅在“主数据库缺失且恰有一个受控 rollback”时自动恢复。数据库与 rollback 并存、多个孤儿、主库缺失但只有 retained recovery，或主库缺失但普通备份目录仍有识别出的快照等状态，都会保留全部现场并停止启动，不自行猜测，也不创建一个看似首装的空数据库。

真正的首次创建会在生成 `backups/` 或打开 SQLite 前，以临时 `wx` 文件、文件 `fsync`、原子 rename 和数据目录 `fsync` 先发布固定内容的 `database-initializing-v1` 意图。若此后崩溃，有效意图可恢复缺失、0 字节或已提交但尚未发布哨兵的首装数据库；这期间不会生成 pre-migration 备份。完整初始化成功后，Main 先以同样的耐久流程发布 `database-initialized-v1` 哨兵，再严格复核并删除意图、同步数据目录，因此“哨兵已存在但意图未删”也可幂等收口。

即使用户从未启用备份，哨兵存在而主库缺失也会 hard-stop；有效意图不能绕过哨兵或已识别备份。为覆盖旧版用户第一次启动 v7 前的升级窗口，Main 还会在准备目录前记录是否已有真实、非符号链接的 `backups/` 目录；旧版本成功启动必然留下这个目录，因此即使它为空且还没有新哨兵或意图，主库缺失也会停止。仅预建的空数据目录不算初始化证据。任何预先存在但为 0 字节且没有有效意图的主数据库同样一律拒绝初始化。对既有主库，Main 会保存打开前的文件身份、大小和修改时间，并在 SQLite 打开后的第一步复核；在该窗口被删除、替换或截断时，不运行 PRAGMA、迁移或初始化。

当前协议不提供“导入为新工作区”式的 ID 合并，也不导入自动化运行历史、终端运行时或机器终端偏好。v11 应用继续接受 v7/v8 `.dwbx` v1、v9 `.dwbx` v2，以及 source schema v10/v11 `.dwbx` v3；所有来源都构建并验证当前 v11 staging schema，其中 v2/v3 的自动化定义强制暂停，v3 的未结束专注也强制暂停。
